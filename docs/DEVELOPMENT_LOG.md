### Issue 1: Resend Email Sending Failure

#### 1. Root Cause Diagnosis
1. **Invalid Sender Domain (`wishes@resend.dev`)**:
   - Both `.env`, `.env.example`, and `render.yaml` were previously configured with:  
     `RESEND_FROM_EMAIL=Wish Yours <wishes@resend.dev>`
   - Resend strictly prohibits sending from arbitrary subdomains or addresses on `resend.dev`. The **only** permissible sender address on their test domain is `onboarding@resend.dev`. Any other address triggers an HTTP 403 / 422 API error.
2. **Environment Variable Clobbering in `server.js`**:
   - The custom `loadEnv()` helper in `server.js` was parsing the local `.env` file and unconditionally overwriting `process.env[key] = value`, even when `value` was an empty string. On Render (or environments where keys are provided via the host dashboard), an empty local file could erase the live API key.
3. **Resend Free Sandbox Recipient Restriction**:
   - When sending from `onboarding@resend.dev` without a verified custom domain, Resend enforces a strict sandbox policy: **emails can only be delivered to the email address registered with that Resend account**.
   - Attempting to send to arbitrary third-party emails fails with an HTTP 403 error:  
     `You can only send testing emails to your own email address...`
4. **Missing Informative Server Diagnostics**:
   - Previously, failures returned generic 500 error messages without explaining why Resend rejected the dispatch or what action the developer needed to take in the Resend dashboard.

#### 2. Implementation & Fixes
- **`api/email.js`**:
  - Implemented `getValidResendSender(configuredFrom)`: auto-corrects any invalid sender on `resend.dev` to `Wish Yours <onboarding@resend.dev>`.
  - Implemented `maskEmail(email)`: masks recipient emails (e.g. `e***n@example.com`) to prevent leaking PII in server logs.
  - Added smart error diagnostics translating Resend HTTP 403 sandbox errors into actionable instructions directing users to verify their custom domain at `resend.com/domains`.
  - Added robust timeout (10s) and network error handling for native `https.request`.
  - Implemented transparent fallback simulation for development environments where `RESEND_API_KEY` is not yet configured.
- **`server.js`**:
  - Refactored `loadEnv()` to prioritize existing live environment variables, strip inline comments and quotes, and ignore empty string values.
- **`render.yaml` & `.env.example`**:
  - Updated `RESEND_FROM_EMAIL` to default to `Wish Yours <onboarding@resend.dev>`.
  - Documented the custom domain verification requirement.
- **`tests/test_resend_live.js`**:
  - Created a dedicated CLI diagnostic tool to verify Resend credentials and test delivery end-to-end.

2. **Absence of User Selection in Creation Studio**:
   - `public/create.html` had no typography selector UI. Users could select occasion, relationship, style, and theme, but had no way to choose a font family.

   - The wax-sealed love letter module in `greeting.js` had hardcoded `font-serif-display` throughout the unfolded letter and memory quotes.
4. **Email Template Lacked Font Styling**:

### Issue 3: Phase 1 — Blank Page Bug & Form Input Contrast Fix

#### 1. Root Cause Diagnosis
1. **Invisible Text & White Background on Form Controls**:
   - The application was referencing Tailwind v3 classes (`bg-slate-900`, `bg-slate-800`, `border-slate-700`, `bg-gray-950`), while loading the legacy Tailwind 2.2.19 CDN.
   - Because `slate-*` classes did not exist in Tailwind 2, browser user-agent defaults applied a white (`#ffffff`) background to `<input>`, `<select>`, and `<textarea>`.
   - Combined with `class="text-white"` (`#ffffff`), this created **white text on a white background** — making inputs and generated messages in `#finalMessageInput` completely invisible to the user.
2. **Greeting Page (`/wish/:slug`) Blank Screen on Errors**:
   - `public/wish.html` initialized `<div id="greetingMainContent" style="display: none;">`.
   - In `public/js/greeting.js`, `renderNotFound(msg)` updated the inner HTML of `mainEl` but never unhid it (`mainEl.style.display = 'block'`). Since `loadingEl` was hidden in `finally`, the page stayed 100% blank without even displaying an error.
   - In `renderPage()`, `wish.theme.includes('romantic')` and `this.wish.relationship.toLowerCase()` threw uncaught TypeErrors whenever `theme` or `relationship` were null or undefined. This crashed JS execution before reaching `mainEl.style.display = 'block'`, leaving the page blank forever.
3. **Missing Studio Live Preview & Direct Navigation**:
   - Step 6 had no real-time visual greeting card preview to confirm the entered names, selected font, theme, and generated message.
   - After creation, users were kept on the wizard step behind a modal instead of smoothly redirecting to the live celebration page.

#### 2. Implementation & Fixes
- **`public/css/styles.css`**:
  - Added global form control rules guaranteeing dark slate (`#0f172a`) backgrounds, crisp white (`#f8fafc`) text, and slate (`#334155`) borders on all inputs, selects, and textareas.
  - Added palette polyfill for `.bg-slate-950`, `.bg-slate-900`, `.bg-slate-800`, `.bg-slate-700`, `.border-slate-700`, and `.bg-gray-950`.
- **HTML Files**:
  - Upgraded Tailwind CDN across all HTML files to Tailwind v3 (`https://cdn.tailwindcss.com`).
- **`public/js/greeting.js`**:
  - Bulletproofed `renderNotFound(msg)` to guarantee `mainEl.style.display = 'block'`.
  - Added defensive null/undefined checks across all fields (`occasion`, `theme`, `relationship`, `recipient_name`, `sender_name`, `message`).
  - Added `renderCreatedBanner()` that displays a celebratory top banner with quick share/copy actions when accessed with `?created=1`.
- **`public/create.html` & `public/js/creator.js`**:
  - Added an interactive **Live Greeting Webpage Preview Card** directly in Step 6, updating in real time as the user types or selects fonts.
  - Configured `publishGreeting()` to smoothly redirect users to `/wish/:slug?created=1` on creation.

### Issue 5: Occasion Emotion Intelligence, Text Grammar Polish & Form Contrast Audit

#### 1. Root Cause Diagnosis
1. **Form Input Readability & Browser Autofill Inconsistencies**:
   - In Chromium browsers (Chrome/Edge on Windows), native inputs and `<select>` elements without an explicit `color-scheme: dark !important;` or browser autofill reset defaulted to `#ffffff` background with white or light text, causing invisible text and illegible dropdowns.

2. **Occasion Emotion Mismatch (Tone Blindness)**:
   - Occasions were previously treated as homogeneous celebrations (e.g., rendering "Let's celebrate your sorry" or celebratory cake animations on apologies).
   - Apologies (`Sorry`), Condolences (`Condolence & Sympathy`), and Gratitude (`Thank You`) require distinct emotional gravity, respectful language, sincere letter layouts, and non-celebratory audio/visual ambient effects.

### Issue 7: Form Control Contrast & Dropdown Bug Root Cause Fix, 7-Step Creation Studio Redesign, and Memory Data Lifecycle

#### 1. Root Causes Identified
1. **White-on-White Dropdown & Input Glitch in Chromium / Windows**:
   - In Chromium on Windows, `<select>` tags assigned Tailwind `text-white` apply `color: white;` to child `<option>` elements via inheritance.
   - However, native Windows select popup menus DO NOT inherit background color from parent CSS classes (`bg-slate-900`). The native Windows dropdown renders options against a white background by default unless `color-scheme: dark !important` is set on `:root`, `html`, `body`, and `<select>`.
   - Result: Unselected options displayed pure white text on pure white backgrounds (completely invisible).
   - Furthermore, `server.js` sent `Cache-Control: public, max-age=86400` on static files, causing browsers to serve stale CSS stylesheets from disk cache rather than revalidating updates.
2. **Details / Memory Form Inputs Bug**:
   - Input fields in `create.html` lacked continuous two-way binding. Values remained isolated in the DOM until `saveStep3Inputs()` was manually called during forward step navigation.
   - Jumping steps or clicking directly to generate bypassed input saving, resulting in blank or empty memory payloads reaching Gemini AI and database records.
3. **Writing Improvement Engine Language & Fact Retention**:
   - AI correction required strict non-translation constraints to ensure conversational Romanized Hindi (Hinglish) and Devanagari Hindi remain in their native scripts without unwanted English translation.

#### 2. Implementation Summary
- **Inlined Critical Form Stylesheet & Cross-Platform Dropdown Polyfill**:

  - Overrode browser autofill via `-webkit-box-shadow: 0 0 0px 1000px #0f172a inset !important`.
