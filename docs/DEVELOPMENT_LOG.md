### Issue 1: Resend Email Sending Failure

#### 1. Root Cause Diagnosis
1. **Invalid Sender Domain (`wishes@resend.dev`)**:
   - Both `.env`, `.env.example`, and `render.yaml` were previously configured with:  
     `RESEND_FROM_EMAIL=Wish Yours <wishes@resend.dev>`
   - Resend strictly prohibits sending from arbitrary subdomains or addresses on `resend.dev`. The **only** permissible sender address on their test domain is `onboarding@resend.dev`. Any other address triggers an HTTP 403 / 422 API error.
2. **Environment Variable Clobbering in `server.js`**:
   - The custom `loadEnv()` helper in `server.js` was parsing the local `.env` file and unconditionally overwriting `process.env[key] = value`, even when `value` was an empty string. On Render (or environments where keys are provided via the host dashboard), an empty local file could erase the live API key.
3. **Resend Free Sandbox Recipient Restriction**:
   - When sending from `onboarding@resend.dev` without a verified custom domain, Resend enforces a strict sandbox policy: **emails can only be delivered to the email address registered with that Resend account**.
   - Attempting to send to arbitrary third-party emails fails with an HTTP 403 error:  
     `You can only send testing emails to your own email address...`
4. **Missing Informative Server Diagnostics**:
   - Previously, failures returned generic 500 error messages without explaining why Resend rejected the dispatch or what action the developer needed to take in the Resend dashboard.

#### 2. Implementation & Fixes
- **`api/email.js`**:
  - Implemented `getValidResendSender(configuredFrom)`: auto-corrects any invalid sender on `resend.dev` to `Wish Yours <onboarding@resend.dev>`.
  - Implemented `maskEmail(email)`: masks recipient emails (e.g. `e***n@example.com`) to prevent leaking PII in server logs.
  - Added smart error diagnostics translating Resend HTTP 403 sandbox errors into actionable instructions directing users to verify their custom domain at `resend.com/domains`.
  - Added robust timeout (10s) and network error handling for native `https.request`.
  - Implemented transparent fallback simulation for development environments where `RESEND_API_KEY` is not yet configured.
- **`server.js`**:
  - Refactored `loadEnv()` to prioritize existing live environment variables, strip inline comments and quotes, and ignore empty string values.
- **`render.yaml` & `.env.example`**:
  - Updated `RESEND_FROM_EMAIL` to default to `Wish Yours <onboarding@resend.dev>`.
  - Documented the custom domain verification requirement.
- **`tests/test_resend_live.js`**:
  - Created a dedicated CLI diagnostic tool to verify Resend credentials and test delivery end-to-end.

### Issue 2: Fonts Not Displaying Correctly Across Application

#### 1. Root Cause Diagnosis
1. **Font Loading Architecture**:
   - Fonts were only declared via `@import url(...)` in `public/css/styles.css` without high-performance preconnect tags in the HTML `<head>`. This caused font swap delays (FOUT) and forced browsers to render fallback system fonts.
2. **Absence of User Selection in Creation Studio**:
   - `public/create.html` had no typography selector UI. Users could select occasion, relationship, style, and theme, but had no way to choose a font family.
3. **Hardcoded Font Classes on Greeting & Envelope Pages**:
   - In `public/wish.html` and `public/js/greeting.js`, `#greetingMessageBody` had a static class `font-serif-display` (`Playfair Display`), overriding whatever tone was desired.
   - The wax-sealed love letter module in `greeting.js` had hardcoded `font-serif-display` throughout the unfolded letter and memory quotes.
4. **Email Template Lacked Font Styling**:
   - Transactional emails generated by `api/email.js` did not inject Google Fonts links or dynamic font stacks into the email body, causing emails to render in standard system sans-serif.

#### 2. Implementation & Fixes
- **High-Performance Font CDN Loading**:
  - Added `<link rel="preconnect">` and Google Fonts `<link rel="stylesheet">` (loading `Playfair Display`, `Dancing Script`, `Great Vibes`, `Outfit`, `Pacifico`, and `Cinzel`) across all HTML files:
    - `public/index.html`
    - `public/create.html`
    - `public/wish.html`
    - `public/dashboard.html`
    - `public/admin.html`
- **Dedicated Typography CSS Classes**:
  - Added explicit utility classes with `!important` and fallback font stacks to `public/css/styles.css`:
    - `.font-playfair`
    - `.font-dancing`
    - `.font-great-vibes`
    - `.font-outfit`
    - `.font-pacifico`
    - `.font-cinzel`
- **Typography Selector in Creation Studio (`public/create.html`)**:
  - Added 6 interactive visual cards in Step 4 with sample font lettering.
  - Added a live font switcher dropdown in Step 6 above the editable message textarea.
- **Creator Controller Typography Management (`public/js/creator.js`)**:
  - Initialized `data.font_family = 'Playfair Display'`.
  - Added `setFontFamily(fontName)`: updates active button styles, updates active badges, updates the Step 6 dropdown, and dynamically applies the font to `#finalMessageInput` so users preview their font choice while typing.
  - Forwarded `font_family` in the wish publish payload and email sharing dispatch.
- **Interactive Greeting Page Typography (`public/js/greeting.js`)**:
  - Implemented `getFontStack()` and `getFontClass()` helpers.
  - Dynamically removed default classes and applied the wish's `font_family` class and inline font-family to `#greetingMessageBody` and `#personalMemoryText`.
  - Updated `openEnvelope()` to render the love letter text, memory excerpt, and sender signature in the selected font.
- **Email Template Typography (`api/email.js`)**:
  - Injected Google Fonts `<link>` into `generateEmailHTML()`.
  - Applied the selected font family stack to the email heading and greeting quote box.
- **Data Layer Sanitization (`api/wishes.js` & `data/db.js`)**:
  - Implemented `sanitizeFontFamily()` to validate against an allowed font whitelist (`Playfair Display`, `Dancing Script`, `Great Vibes`, `Outfit`, `Pacifico`, `Cinzel`) and safely fall back to `Playfair Display` on invalid input.
  - Updated `createWish()` and `updateWish()` to persist and sanitize `font_family`.

### Issue 3: Phase 1 — Blank Page Bug & Form Input Contrast Fix

#### 1. Root Cause Diagnosis
1. **Invisible Text & White Background on Form Controls**:
   - The application was referencing Tailwind v3 classes (`bg-slate-900`, `bg-slate-800`, `border-slate-700`, `bg-gray-950`), while loading the legacy Tailwind 2.2.19 CDN.
   - Because `slate-*` classes did not exist in Tailwind 2, browser user-agent defaults applied a white (`#ffffff`) background to `<input>`, `<select>`, and `<textarea>`.
   - Combined with `class="text-white"` (`#ffffff`), this created **white text on a white background** — making inputs and generated messages in `#finalMessageInput` completely invisible to the user.
2. **Greeting Page (`/wish/:slug`) Blank Screen on Errors**:
   - `public/wish.html` initialized `<div id="greetingMainContent" style="display: none;">`.
   - In `public/js/greeting.js`, `renderNotFound(msg)` updated the inner HTML of `mainEl` but never unhid it (`mainEl.style.display = 'block'`). Since `loadingEl` was hidden in `finally`, the page stayed 100% blank without even displaying an error.
   - In `renderPage()`, `wish.theme.includes('romantic')` and `this.wish.relationship.toLowerCase()` threw uncaught TypeErrors whenever `theme` or `relationship` were null or undefined. This crashed JS execution before reaching `mainEl.style.display = 'block'`, leaving the page blank forever.
3. **Missing Studio Live Preview & Direct Navigation**:
   - Step 6 had no real-time visual greeting card preview to confirm the entered names, selected font, theme, and generated message.
   - After creation, users were kept on the wizard step behind a modal instead of smoothly redirecting to the live celebration page.

#### 2. Implementation & Fixes
- **`public/css/styles.css`**:
  - Added global form control rules guaranteeing dark slate (`#0f172a`) backgrounds, crisp white (`#f8fafc`) text, and slate (`#334155`) borders on all inputs, selects, and textareas.
  - Added palette polyfill for `.bg-slate-950`, `.bg-slate-900`, `.bg-slate-800`, `.bg-slate-700`, `.border-slate-700`, and `.bg-gray-950`.
- **HTML Files**:
  - Upgraded Tailwind CDN across all HTML files to Tailwind v3 (`https://cdn.tailwindcss.com`).
- **`public/js/greeting.js`**:
  - Bulletproofed `renderNotFound(msg)` to guarantee `mainEl.style.display = 'block'`.
  - Added defensive null/undefined checks across all fields (`occasion`, `theme`, `relationship`, `recipient_name`, `sender_name`, `message`).
  - Added `renderCreatedBanner()` that displays a celebratory top banner with quick share/copy actions when accessed with `?created=1`.
- **`public/create.html` & `public/js/creator.js`**:
  - Added an interactive **Live Greeting Webpage Preview Card** directly in Step 6, updating in real time as the user types or selects fonts.
  - Configured `publishGreeting()` to smoothly redirect users to `/wish/:slug?created=1` on creation.
- **`server.js` & `data/db.js`**:
  - Modernized `requestHandler` to use the WHATWG `URL` API (eliminating deprecation warnings).
  - Enhanced route regexes to handle optional trailing slashes (`/wish/:slug/`).
  - Implemented case-insensitive lookup in `getWishBySlug()` and `getWishById()`.
- **`tests/test_flow.js`**:
  - Added an automated end-to-end trace runner validating data flow from user entry to AI generation, storage, slug creation, and retrieval.

### Issue 4: Phase 3 — Scheduled Wishes Feature & Indian Telecom Architecture

#### 1. Architecture & Design Requirements
1. **User Flow**:
   - Provide "Send Now" and "Schedule for Later" buttons in Step 6 of Creation Studio, on `/wish/:slug`, and in the Share Modal.
   - Dedicated scheduling modal with recipient name, recipient email / phone with country code, date, time, timezone selector (auto-detecting user timezone), delivery method (Email, SMS, Voice Call), and optional personal delivery note.
   - Dynamic confirmation preview banner updating live: *"Your Birthday wish for Priya will be sent via Email on 15 March 2026 at 09:00 AM IST"*.
   - Success confirmation screen displaying scheduled time in recipient local time with UTC timestamps.
2. **Server-Side Scheduler Engine**:
   - Must run continuously without requiring the sender's browser to remain open.
   - Zero-dependency in-process ticker (`scheduler/engine.js`) coupled with an atomic idempotency lock (`db.lockScheduledWish()`).
   - Support for external cron webhook (`/api/cron/process-scheduled`) with `x-cron-key` security header to wake Render free tier instances and trigger batch dispatches.
3. **Delivery Provider Abstraction**:
   - **Email**: Resend API integration (`api/providers/email_provider.js`) with responsive celebration styling, typography, and unwrap button.
   - **SMS**: Provider abstraction (`api/providers/sms_provider.js`) supporting Twilio, Fast2SMS (India), and simulated development fallback.
   - **Voice Call**: Programmable voice abstraction (`api/providers/voice_provider.js`) supporting Twilio Voice with TwiML Text-To-Speech (TTS).
4. **Dashboard Management**:
   - Multi-tab navigation in `public/dashboard.html` ("All Celebrations 💌" vs "Scheduled Wishes ⏰").
   - Detailed status badges (`scheduled`, `processing`, `sent`, `failed`, `cancelled`).
   - Actions to view celebration webpage, reschedule/edit date & time, cancel schedule, and delete records.

  - `GET /api/cron/process-scheduled`: Secured cron trigger endpoint.
- **Background Scheduler (`scheduler/engine.js`)**:
  - Batch size 25 with 30-second polling interval.
  - Atomic idempotency locking preventing duplicate dispatches.
  - Automatic retry with 2-minute backoff for transient failures (up to 3 attempts).

### Issue 5: Occasion Emotion Intelligence, Text Grammar Polish & Form Contrast Audit

#### 1. Root Cause Diagnosis
1. **Form Input Readability & Browser Autofill Inconsistencies**:
   - In Chromium browsers (Chrome/Edge on Windows), native inputs and `<select>` elements without an explicit `color-scheme: dark !important;` or browser autofill reset defaulted to `#ffffff` background with white or light text, causing invisible text and illegible dropdowns.
   - Date and time picker icons lacked inverted contrast filters on dark slate backgrounds.
2. **Occasion Emotion Mismatch (Tone Blindness)**:
   - Occasions were previously treated as homogeneous celebrations (e.g., rendering "Let's celebrate your sorry" or celebratory cake animations on apologies).
   - Apologies (`Sorry`), Condolences (`Condolence & Sympathy`), and Gratitude (`Thank You`) require distinct emotional gravity, respectful language, sincere letter layouts, and non-celebratory audio/visual ambient effects.
3. **Messy User Notes Compromising AI Quality**:
   - Users frequently type informal shorthand or unpunctuated notes (e.g., `"we was frnds from collage and you always suport me when i was sad"`). Without pre-cleaning, grammatical errors cascaded into AI-generated greetings.
   - Critical requirement: Cleaning must strictly preserve all user facts, names, dates, inside jokes, and original sentiment without fabricating generic details.

#### 2. Implementation Summary
- **Master Dark Form Control System (`public/css/styles.css`)**:
  - Enforced `color-scheme: dark !important;` globally.
  - Set `#0f172a !important;` background and `#f8fafc !important;` text on all `input`, `select`, and `textarea` controls.
  - Overrode browser `-webkit-autofill` with dark slate inset box-shadows.
  - Custom SVG arrow indicator and dark dropdown option styling for native `<select>`.
  - Date and time picker icon inversion filters for crisp contrast.
- **Occasion Emotion Intelligence Engine (`data/occasions.js` & `public/js/occasions.js`)**:
  - Defined comprehensive metadata for 12 occasions across 7 emotional categories (`celebration`, `romantic`, `apology`, `gratitude`, `achievement`, `nostalgia`, `sympathy`).
  - Added strict negative constraints (`forbiddenKeywords`) blocking celebratory words (`celebrate`, `happy sorry`, `party`, `blast`) on apologies and condolences.
  - Configured occasion-appropriate visual modules (`cake`, `envelope`, `sincere_letter`, `friendship_card`), ambient particle effects (`balloons`, `hearts`, `calm_droplets`, `petals`), and music tracks (`birthday_celebration`, `romantic_melody`, `peaceful_melody`).
- **Text Improvement & Grammar Polish Engine (`data/text_cleaner.js` & `server.js`)**:
  - Dual-mode cleaner: Gemini AI-assisted polish + robust rule-based dictionary fallback.
  - Cleans typos (`frnds` -> `friends`, `collage` -> `college`, `suport` -> `supported`), corrects subject-verb agreement (`we was` -> `We were`), capitalizes sentences and standalone 'I', and ensures proper punctuation.
  - Zero-hallucination constraint: strictly retains all user-entered facts and memories.
  - Added `POST /api/correct-text` endpoint for client-side interactive suggestions.
- **Studio Creation Experience (`public/create.html` & `public/js/creator.js`)**:
  - Added interactive "✨ Polish Grammar & Typos" tool in Step 3 personal details with side-by-side "Original vs Improved" suggestion box and single-click "Apply Improved Version".
  - Added "✨ Polish Text" tool in Step 6 final message editor.
  - Dynamically updated occasion badges, guidance copy, and live previews via `OccasionManager.resolve()`.
- **Greeting Webpage Overhaul (`public/wish.html` & `public/js/greeting.js`)**:
  - Implemented `renderSincereLetterModule(occMeta)` for apologies, thank-you notes, and condolences.
  - Dynamic page title and header badges adapting to emotional tone (e.g., "Heartfelt Apology 🕊️" instead of "Celebration").
  - Connected `AmbientParticles` (`calm_droplets`, `petals`) and `SoundEffects` (`playPeacefulMelody()`).
- **Gemini Prompt Engineering Overhaul (`api/gemini.js` & `api/generate-message.js`)**:
  - Injected structured system instructions with strict negative constraints.
  - Built comprehensive fallback templates across English, Hindi (`hi`), and Hinglish (`hinglish`).
